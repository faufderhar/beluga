# Tasks, Plans and Graphs (Mac app) — design

Three features that build on each other:

1. **Graphs.** The agent draws interactive diagrams (React Flow) in any conversation, document or recap.
2. **Tasks.** A Linear-quality board shared with friends. Every worktree is a task, every task knows its PR, and agents read and improve each task's brief while they work.
3. **Plans.** Milestones → phases → tasks, with blockers, parallel lanes and review gates. You plan with the agent using your own planning instructions. A head agent then runs the plan: it starts worktrees in parallel and stops for you wherever you ask it to.

Graphs ship first because the other two use them: plans are drawn as graphs, and milestone recaps explain what happened with graphs and proof.

The core holds the state and the agent tools; the Mac app shows them (see [parity.md](parity.md) › "Beyond the shared actions").

---

## 1. Graphs (`beluga-graph`) — phase 1, shipped first

The agent writes a fenced block of JSON and the window draws it. No code runs, so a graph is only data:

````
```beluga-graph
{ "title": "How a login works", "direction": "right",
  "nodes": [ { "id": "app", "type": "client", "label": "Mac app" }, … ],
  "edges": [ { "from": "app", "to": "api", "label": "POST /login", "kind": "call" } ],
  "steps": [ { "title": "1. The app asks", "focus": ["app", "api"], "text": "…" } ] }
```
````

- **Where graphs show up:** chat answers, Markdown files in the reader, reports, task briefs and milestone recaps.
- **How it starts:** `/visualize <what>` asks the agent for a graph. The agent can also decide on its own: the system prompt says when a graph helps and what the format is.
- **Node kinds:** `client`, `service`, `database` (with fields), `queue`, `storage`, `external`, `actor`/`person`, `function`, `file`, `decision`, `note`, `task` (with status), `milestone`, `image` (a screenshot as proof), `metric`, and `group` (a labelled box around other nodes).
- **Edge kinds:** `flow`, `call`, `data`, `async` (moving dashes), `depends` and `blocks`, each with an optional label.
- **Layout:** automatic, with ELK's layered algorithm and groups as compound nodes. The agent never writes coordinates.
- **Working with a graph:**
  - pan, zoom and fit
  - hover a node to light up its neighbours
  - click a node for its details: Markdown, links to files, tasks and URLs
  - **Walkthrough** (`steps`): one step at a time, each focusing a few nodes and edges with a caption
  - open full window, with a minimap
  - change the direction
  - Copy as JSON
- **Look:** the window's own tokens, neutral greys with color only for meaning (status, the agent's copper), light and dark, reduced motion respected.
- **Safety:** zod validates every block. A block that doesn't validate shows a readable error with its JSON. Markdown in details goes through the chat's sanitizing renderer, and image nodes follow the chat's image rules (local pictures only in your own and your agent's messages).

Spec and examples: [graphs.md](graphs.md). Code: `src/shared/graph-spec.ts` (browser-safe schema), `packages/mac/src/components/graph/*`.

## 2. Tasks — phase 2, shipped

### The model (`src/core/board/`, browser-safe slice `board`)

The gateway already uses the word "tasks" in code, so this feature's code says **board** and **issue**. The window says **Tasks**. Everything lives in `~/.beluga/board.json` (only you can read it), written a moment after each change.

| Field | Notes |
|---|---|
| `key` | `BOB-12`: its board's prefix (from the name, changeable with `board.setPrefix`) and a counter |
| `projectId`, `board` | the repo it runs in (Start makes its worktree there), and the board it's on when that isn't its repo's own (BLG-500, below) |
| `title`, `status` | Backlog · Ready · In Progress · In Review · Done · Canceled (the board's columns) |
| `priority`, `labels`, `estimate`, `due` | Linear's set (estimates 1, 2, 3, 5, 8) |
| `assignee` | a person: you or a friend (peer id), never an agent (BLG-278; an older one for someone's agent reads as theirs). Who's on it now shows on its own, under its card |
| `parent` | sub-tasks; a task can't sit under itself or its own sub-tasks |
| `blockedBy`, `related` | what must be done first (its other side is "blocks"; a loop is refused), and related tasks |
| `worktrees`, `branch`, `pr` | the worktrees doing it (the current one last), its branch, and its pull request as the workbench last saw it |
| `brief` | the living definition (below), with revisions |
| `proof` | screenshots, pages, files, graphs and results, attached by people or the agent |
| `activity` | an append-only feed: who changed what, comments, the agent's notes, pull request events (the last 200). One field changed again by the same person within two minutes is one line ("estimated this at 5 points", from where it started; back where it was, no line) |
| `plan` | the plan, milestone and plan task it came from |

**Boards and repos are many to many (BLG-500).** Every repo has a board of its own (keyed by its project id in `board.json`'s `projects`), and a board can cover more repos (`repos`); a board of its own (`board_…`, made with New Board… in the board switcher) covers only the repos it names and has a `name`. A task is on one board (`boardOf`: its `board`, else its repo's) and runs in one repo. Its key, labels and About This Board come from the board; Start, the worktree, team boards and Linear sync go by its repo. New work goes on the board you're on (New Task, an agent working a task there); with nothing to say which, it lands on its repo's own board, never somewhere guessed (BLG-560); a sub-task is on its parent's board, in whichever repo. Moving a task to another repo keeps its board and key, and a board takes in a repo once a task there runs in it. A repo's own board shows every task that runs in its repo, wherever it lives: one on another board shows there too, a shade back with a chip naming its board that opens it (`showsOn`, `isVisiting`; the phone says `on Launch`), and Archive Done and Empty Archive take what the board shows (BLG-559). So every repo's board is always in the switcher. The window shows one board at a time; on a board of several repos a **Repos** filter picks whose tasks show (all by default), each card says its repo, New Task asks for the repo, and a task's page has a Repo menu. Agent runs on such a board are told its repos (`reposPrompt`): `task_create` puts a task on the run's board in its repo, `project` names another repo, `board` another board, and `task_list` says each task's repo. **An epic across repos starts as one (BLG-561):** Start on an epic whose unfinished sub-tasks run in other repos makes a worktree in each of those repos too, under the same name and quietly (`BoardWork.startAlong`), and links those sub-tasks to it, so each repo's pull request moves its own sub-tasks. One agent, in the epic's worktree, works in all of them: the workspace's place lists them as extra folders it edits without asking (`WorkspaceController.setAlsoIn` → `AgentPlace.alsoEdit` → the policy's `alsoEdit`), and every run there is told their folders and branches and to commit in each (`alongPrompt`). The task page says so before Start ("A worktree in bob-api and landing…") and after ("also in landing"). A teammate's tasks arrive on your repo's own board (boards are yours; the team shares repos).

**The brief** is what later agents rely on. It's Markdown in fixed sections: **Goal**, **Context**, **Acceptance criteria** (checkboxes you tick on the page; one that can't be true yet carries its reason on its line, `- [ ] … — deferred: why` or `— not done: why`, and shows as Deferred or Not done), **Decisions** (what was decided and why), **Open questions** and **Notes for the next agent**. Each edit is a revision with its author (a person or an agent) and a one-line reason. A section's history shows every version; **Restore This** puts one back (as a new revision).

### Worktree ↔ task (automatic)

- **Tasks come from plans, not from every worktree.** A question or a quick ask is not a task.
  - **Plan First** (Claude Code's plan mode): before the agent asks you to approve its plan, it calls `task_define` with the task the plan is for — a title, the goal *in its own words* (never your message pasted in), context, acceptance criteria, decisions, open questions, an estimate and a priority. It goes on the board only when you approve the plan (`planTask` in `agent/runner.ts`); a plan the agent asks you to approve without one goes back to it once. Approved in a main folder's chat, the task waits and the worktree the conversation continues in does it.
  - **Plan with Tasks** (Plans, below): every task of an approved plan.
  - A fork stays on the same task, as does a worktree started *from* a task (Start).
  - Tasks › ⋯ › Agent Opens a Task for Worktree Work (off by default; saved as `worktreeTasks`): a new worktree still opens no task by itself, but its agent decides. When the work will ship (a fix, a feature, a pull request), it opens the worktree's task with `task_define` before starting; a question or a look around gets none. That task is **private** (only you see it until Share with Team) and **assigned to you**, and the agent says it opened it and that it's private.
- **The task follows the work:**

  | When | Status |
  |---|---|
  | The worktree is created | In Progress |
  | A pull request opens (not a draft) | In Review |
  | Changes are requested | back to In Progress, with a note |
  | The pull request merges, or the worktree merges into main here | Done |
  | Archived or deleted before it was done | a banner asks: Cancel Task, Back to Backlog, or Keep As Is |
  | Its parent reaches Done | Done (every open sub-task, all the way down; Canceled ones stay) |
| Its sub-tasks move (Canceled ones left out) | a parent follows them: In Progress once one is under way, In Review when all are in review or done, Done when all are Done, and back to In Progress when one opens again or a new one comes; all the way up. A parent with a worktree or pull request of its own goes no further than In Progress (its own work takes it on); a plan's task or a canceled one stays put |

  A merged PR settles a chat only for worktrees Beluga polls for pull requests: kind `worktree`, with a branch and Beluga as its origin. A plan's row settles only from the plan's own PR, never from a task worktree's.

- **Work carried by another worktree** (BLG-29). When the agent moves a task to In Progress or In Review from a worktree that isn't doing it (the sub-tasks of a list of asks, done in one worktree), that worktree *carries* it (`carriedBy`, and its branch). The carrying worktree's pull request and merge move the task like its own. Tasks whose worktree went before their PR merged aren't watched by the workbench any more: `BoardWork.sweepShipped` asks gh about their branch soon after start and every ten minutes, and a merged PR makes them Done.
- **The Archive** (BLG-27, BLG-28). Archive Done (the button on Done, in the list and on the board, or Tasks › ⋯) moves every Done task to the Archive (`archivedAt`); a finished task's ⋯ › Archive moves one, with its finished sub-tasks. Archived tasks leave the board and the agent's `task_list` but keep their brief and history: Tasks › Archive lists them, a task's banner restores it, and Empty Archive (or Delete for Good) deletes them. Archiving lets go of their proof files in `~/.beluga/proof`: a screenshot becomes a 480 px JPEG (`thumb`, a few KB), any other file goes (`gone`); both keep how big they were (`bytes`). Files outside `~/.beluga/proof` are never touched.

- **The agent knows its task.** Your own runs in a task's worktree get its brief, parent, blockers and sub-tasks in their instructions (`core/board/prompt.ts`), and the task tools (server `beluga_board`), built for each run from its conversation:
  - `task_get`, `task_list`, `task_create` (sub-tasks, follow-ups), `board_create` (a board for work across a few repos, made without the user opening New Board first), `task_update`, `task_brief_edit` (a section, a reason, replace or append), `task_note`, `task_relate`, `task_attach_proof`.
  - The agent is told to record decisions as it makes them, tick acceptance criteria, split off work as sub-tasks, attach proof, and rewrite the notes for the next agent before ending a turn that changed things. It doesn't mark tasks Done itself unless you ask or say the work shipped: the pull request does.
  - Every run hears how the board works, and to open tasks unasked when one message asks for two or more separate things (one per thing, under a parent when they belong together), move them along as it works, and show them in its answer as `task:KEY` chips or a `beluga-tasks` block. Not for questions or a single quick ask, and what you ask for instead wins (BLG-25).
  - Runs elsewhere get the tools and a short note that the board is there. A main folder's chat gets them too (the folder stays read-only), and so does a plan's own conversation, for work outside the plan. Syncing main and a milestone's checker get neither. The tools only touch your own board, so they never ask; files holding secrets are refused as proof.

### Sync with Linear (BLG-74)

A project's board can be linked to one Linear team, and kept in step both ways (`src/core/board/sync/`).

- **Connecting:** Tasks › ⋯ › Sync with Linear…. Paste a personal API key (`lin_api_…`), Check Key lists the workspace's teams, pick one, and choose **Autosync** (on by default) and **Also send this project's open tasks** (off: only tasks made from now on go to Linear). The key is kept in `~/.beluga/task-sync.json` (0600) and never reaches a screen or the phone. Screens get `board.sync[projectId]`: the team, autosync, when it last synced, how many tasks are linked, and what went wrong.
- **What comes over:** on the first sync, the team's open issues and those closed in the last two weeks. After that, everything changed since the last look. Each becomes a task (`origin: 'sync'`, "Linear brought this task over") linked to its issue (`issue.link`: the id, `ENG-12` and its URL).
- **What goes out:** tasks made in the project since connecting (and its open ones from before, when asked), parents first. Drafts wait until the agent has written them, and archived tasks stay here.
- **Kept in step:** title, status, priority, labels, estimate, due date, parent, and the brief as the description. The description is the goal first, then each other section under its heading (`## Acceptance criteria`). Reading one back, text under a known heading goes to that section and everything else to the goal.
  - **Status:** Backlog/Triage ↔ Backlog, Unstarted ↔ Ready, Started ↔ In Progress (a started state named "…Review…" ↔ In Review; Merged into Plan goes as In Review), Completed ↔ Done, Canceled ↔ Canceled.
  - **Priority:** Linear's 0–4.
  - **Labels:** matched by name, any case; missing ones are made as team labels.
  - **Estimates:** only sent when the team uses them.
- **Who wins:** each link keeps a fingerprint of every field on both sides as they last agreed (`link.local`, `link.remote`). A field only one side changed goes to the other. When both sides changed it, the newer change wins. A side whose value can't say what the other's does (Merged into Plan) doesn't bounce back. Changes from Linear show in the activity as by **Linear**, and brief edits keep their revisions, so Restore This brings back what Linear overwrote.
- **Autosync:** Linear can't call a Mac back, so Beluga asks every minute (`AUTO_MS`), soon after starting, and a few seconds after a change here to a linked or sendable task (`SOON_MS`). A key Linear turns down stops autosync until you connect a new one (the bar's Linear pill says so). Sync Now is in ⋯ and the sheet.
- **Disconnecting** forgets the key and unlinks the tasks. Nothing in Linear changes. Connecting another team unlinks the old team's tasks first.
- **Other trackers:** `sync/provider.ts` is the seam: teams, changed-since, create, update, in the board's terms. GitHub Issues is BLG-75.
- The agent sees a task's Linear key and URL in its brief (`prompt.ts`). `BELUGA_LINEAR_API` points the daemon at a fake Linear for testing.

### GitHub issues (BLG-163)

A project's GitHub issues, read in Beluga and handed to the agent (`src/core/issues/`, the Mac's `src/issues/`). This isn't sync (that's BLG-75): nothing in GitHub changes unless you post a comment. Every way of working on an issue goes through **a task**, so the work shows on the board, its worktree and conversation are the usual ones, and its pull request moves it along.

- **Reading:** through gh, signed in as you (`src/core/issues/gh.ts`): GraphQL for a project's open or closed issues, newest activity first (REST's list counts pull requests against the page), GitHub's search when you search (`is:issue`), REST for one issue and its comments. gh is only asked about github.com and hosts it's signed in to. Not on GitHub, gh missing or signed out, and GitHub saying no each come back as their own state (`IssuesList`), in Beluga's words (`ghWords`). Lists are kept a minute (Refresh asks again).
- **Where:** **Issues** in the sidebar under Tasks (one project at a time, the one you're in; Open · Closed; search; ⌘K › Go to Issues), the latest three on a project's home (or a line saying none are open, with Show All Issues), and an issue's page (`gh_issue`): the report and its comments, and what to do next.
- **What to do next**, until the agent is on it, is a composer like a project's home (`IssueComposer`): Investigate · Fix It · Make a Task, a box for anything the agent should know (it goes after the agent's instructions in your words, and shows in the conversation), one line saying what happens, and one button (↩):
  - **Investigate:** a task for the issue (`origin: 'github'`, `issue.github`: the repo, number and URL), a worktree for it (quietly: you stay on the issue), and your agent told to find out what happens and why, reproduce it (a failing test if it can), write what it found into the task's brief (context and criteria) and stop before fixing (`investigatePrompt`). The page shows the agent at work, then its report (what happens, why, how to reproduce, how to fix, a verdict) with **Fix It**.
  - **Fix It:** after an investigation, in the same worktree and conversation (`fixAfterInvestigationPrompt`); otherwise in a new one (`fixPrompt`). The agent opens the pull request with your PR instructions (`buildPrPrompt`, beluga.json's `prPrompt` too) and "Fixes #n", so merging it closes the issue on GitHub and makes the task Done. Fix It is also on the task's page and the strip above its conversation once the agent has investigated.
  - **Make a Task:** on the board as Ready, written by your agent from the issue (the drafter), or, with **Look at the code first** ticked, after a quick look: the drafter reads the main folder first with Read, Grep and Glob only (a PreToolUse hook refuses anything else, outside the folder, or a secret: `lookVerdict`), and adds context (where the code is, the likely cause). The task shows "Your agent is writing…" meanwhile.
- **One task per issue:** asking again works on the one there is (a done or canceled one is reopened first, on its page). `taskForGitHub` finds it.
- **What it's at** (`issueStage`, from the task): new, on the board, investigating, investigated, fixing (or stopped before a pull request, with what the agent said), its pull request open, done. Rows in Issues and on the project's home show it as a pill.
- **The conversation shows a short line** ("Investigate #48 …: find out why it happens and reproduce it, without fixing it yet"): the agent gets the issue quoted as material (`<github_issue>`, never instructions, GitHub names never "@name": in Beluga that's a friend), with the steps (`askOwnClaude`'s `echo` as a string).
- **A task from an issue** links back to it: a GitHub row on its page, `◉ #48` on its rows and its strip, and the agent's start prompt and `task_get` name the issue, how to read its comments (`gh issue view`), and that its pull request says "Fixes #n".
- **Pull requests on a project's home** (BLG-602): the latest four open ones, anyone's: a title, a line (Draft, number, author, branch), a mark each for its review and checks (their words on hover) and when it last moved. One on a worktree's branch opens that worktree. Any other has **Open in Worktree** (in place of the marks while you're on the row, and in its •••, BLG-633): its branch checked out in a new worktree named pr-<n> and the first words of its title, which opens with a line saying what it is. No agent starts: you look, run it, or ask. A pull request from this repository gets its own branch, tracking origin's, so a push there updates it. One from a fork comes from GitHub's pull ref (`refs/pull/<n>/head`), on its branch's name (pr-<n> when that's taken), and `git pull` brings its new commits.
- **Posting what the agent found:** an issue's ⋯ › Post the Findings on GitHub… (asks first, shows what goes) comments as you.
- **The demo** has a pretend GitHub (acme/bob-api, acme/landing) and a demo agent that investigates and fixes #48.

### Sharing with friends — phase 3: team boards (BLG-220, shipped)

Two friends who each have the same GitHub repository as a project on their own Mac work on it as a team, **without sharing the project**. Code: `src/core/team/` (the daemon runs it with the board, whenever the network is on), the Mac app's `src/team/`. Features: `team.board`, `team.plans` (a friend on an older Beluga is told "Ata's Beluga 1.2.0 can't open team boards yet. Ask Ata to update Beluga.").

- **Finding each other** (`fingerprint.ts`, `service.ts`). On every link to a friend, each Mac sends the fingerprints of its GitHub projects: HMAC-SHA-256 of `host/owner/repo` (lowercased, from the origin remote), keyed by SHA-256 of both peer ids, cut to 128 bits. A friend who has the repository computes the same fingerprint. One who doesn't sees a string they can't turn back into a name (they could only check a name they guess). A match is an offer on both Macs, "Ata also works on acme/api": a strip on the project's home and atop its Tasks (Team Up; ••• › Not Now), a notification, and a card on the phone. Team Up sends an invite. The team forms only when the other side says yes too (two yeses crossing settle on the smaller link id). Not Now and Leave Team hide the offer until either asks again.
- **A team** is one group per project (BLG-510). Teaming up is still done in pairs (`~/.beluga/teams.json` keeps your own links), but the group those pairs join is the team: a friend of Ata's who teams up with Ata is on your team too, though you two aren't friends. Every Mac keeps the group's roster (`roster.ts`, `~/.beluga/team-roster.json`): a line per member, last-writer-wins on its time, "on" said by the member and "off" when they leave the whole team, passed on over the links in a `roster` frame like the board's changes (on every link-up too). So everyone sees everyone: the team badge's names, the people you can give a task to, New Task's "for", Whose Tasks. Someone on it through others is `indirect`: you two aren't friends, and your changes reach them through the others. Friends on the same team link up by themselves (no offer to answer), so knocking and sharing a chat work between any two friends on it; you knock on friends only. To befriend someone on the team, click the team badge on the project's row, or the faces beside Active and Backlog on its board (BLG-906: you and everyone on the teams of the board's repos, a few faces then +N): either lists everyone, and someone's card has **Add Friend** when they aren't a friend yet. That makes a one-time friend invitation only they can use and passes it to them through the team (`befriend` frame; each Mac passes one on once, only between people on the roster). They see "Kay from the acme/api team wants to add you as a friend" (the Friends list, the bell, a card on the phone) and are only added if they Accept. Anyone on the team can invite: project ••• › Invite to Team ▸ lists friends with the repository who aren't on it, and the invite says who's on it already ("Ata invited you to the acme/api team, with Kay"). When someone joins through another member, the others hear "Mia joined the acme/api team". ••• › Leave Team (or leaving your last link) leaves it for everyone: a `leave` frame with `all`, and the teammates you told put you "off" on the roster for the rest. A change reaches everyone even if two of them aren't friends, because each Mac passes on what the others haven't seen.
- **How changes travel.** Over friends' links in a `team` frame, through friend-share's acked courier (`Courier<M>`, its own `team-outbox.json`: resent every 20 s while linked, at once on link-up, for 7 days). This is not option B's hidden group. The courier was already tested and needs no new group plumbing, nothing shows up in channel lists, and team membership is the links themselves.
- **How copies agree** (`crdt.ts`, `board-sync.ts`). Each task field is last-writer-wins by (Lamport time, author peer id), with the brief as one field per section. Activity and comments only get added, by id; a line its author folded into the next is dropped for everyone. A delete is a field too. Every change to a teamed project's task is caught as it reaches the shared state (you, the agent's task tools, a plan, a pull request), so nothing needs to call sync. What arrives is written to the board quietly, and brief sections keep their revisions ("from a teammate"), so Restore This works. Changes made while the network was off go out when it starts again. On every link-up both sides swap a digest of the field clocks, and a different one is answered with a snapshot in batches. Kept in `~/.beluga/team-board.json`.
- **Keys never clash.** A task has one id on every Mac. Each Mac gives it a key from its own project ("API-40" there may be "BLG-12" here). Teaming up shares the board as it is (archived tasks stay yours).
- **What never travels:** worktrees, branches, pull requests, proof files, ranks, the Archive, run details, and activity about worktrees, plans or proof. Teammates see "Ata is working on this" (`working.<peerId>`, true while one of Ata's worktrees does the task), on the task's page, its row and the phone.
- **Assigning** (`assign.ts`). Give a task to a teammate and it's in their My Tasks, with a notification and an inbox entry ("Ata gave you this task", Got It; a card on the phone) until they've seen it. Give it to **a teammate's agent** and the Mac where you assigned it sends a request to their agent (the gateway's `ask`, as you, in their project) with the task's brief. Their trust, rules and approval card apply. The result lands on the task as proof (the summary, the files) and a note from their agent, and the note reaches the whole team. A teammate whose Beluga isn't taking requests gets a note on the task saying so.
- **Issues.** Which GitHub issue became which team task travels with the board (`github`: the issue and the step), so an issue's row says "Ata is investigating #48" with Ata's avatar. Investigate or Fix It on an issue a teammate is on asks first (Start Anyway; the API's `anyway`).
- **Plans** (`plan-share.ts`). A plan stays yours until its ••• › Share Plan with Team. Teammates then see its draft (or what was approved) read-only, in Plans under "Shared by your team": milestones, criteria and tasks. There they Approve (the main action), comment, or Suggest a Change… on a task (the plan's own edit ops). You're notified. Team Reviews on the plan's page lists what they said, with Apply (one click, as your edit; Set Aside under •••). Every change to the plan reaches them as it happens, and Stop Sharing takes it back. On the phone: approving a shared draft (or commenting) and applying or setting aside a suggestion are cards.
- **Private tasks** (BLG-501). A task can be yours alone on the shared board (`private: true`): it never reaches teammates or Linear. Make it private from its ⋯ › Make Private (only offered when someone else would see it), New Task's **Who Sees It** (Only You), or by asking for it in the words ("just for me", "keep it private", "don't share": `asksPrivate`, so it's private before anything could go out; the sheet's own choice wins). The agent's `task_create` takes `private` too. A private task's sub-tasks are private, and a task moved under one becomes private, so a private epic is a board of your own inside the shared one. **Share with Team** (its ⋯, or the button on its page) sends it and its sub-tasks as they are now. Making a shared task private takes it back: teammates get a `deleted` field, and sharing again is `deleted: false`, newer, so it comes back with everything their copies kept. A teammate's change to it while it's private never touches yours. Linear leaves it alone both ways until it's shared (one made private now is sent once it's shared). On screen: a lock by its key, a dashed edge and a face a shade back on its card, a banner on its page, a lock on the phone, and Whose Tasks › Private. Chats with teammates can't @ it, and Claude is told it's private.
- **Chats stay private.** Teaming up never shares a conversation or a worktree. A team project's conversation has ••• › Share with Team ▸ (a teammate, or Everyone on the Team), which shares that one worktree live (`sharing.shareWithFriend`), and Stop Sharing. Its header shows who can see it (their avatars), or a lock when only you can.
- **Knocking** (`knock.ts`, BLG-416, feature `team.knock`). After "Ata is working on this" on a task's page, Knock to Join sends `knock` to Ata's Mac (if several teammates are on it, you pick whose worktree). Ata's Mac finds the worktree doing the task and posts a line in its chat with a card under it: Let In as Editor (the main action), Let In as Viewer, and ••• › Not Now. It also notifies (the bell, and a NeedsYou card on the phone, `wt-knock:<id>`). Letting someone in shares that one worktree with them through `sharing.shareWithFriend` at the role picked, so its chat and files work the way any shared worktree does. The `knock_answer` goes back, and the guest's Mac opens the worktree once it arrives (if they knocked in the last 15 minutes). Until then, the task's page says how the knock stands: waiting (Take Back, which sends `knock_cancel`), let in (Open), or not now (Knock Again). Knocks answer themselves in two cases: someone already in gets back in as they were, and a task no worktree does any more is answered `gone`. Knocks are kept in `~/.beluga/team-knocks.json` for a day.
- **Limits:** a teammate can claim any author in what it sends (teammates are trusted friends). Proof files don't travel. The fingerprint can't stop a friend from confirming a guessed repository name.

### The window (`packages/mac/src/tasks/`)

- **One project at a time.** Tasks from different projects never share a screen. ## 3. Plans and the head agent — phase 4 and 5, shipped

### The model (`src/core/plans/`, browser-safe slice `plans`)

- **A plan** is a goal cut into **milestones**, which run side by side unless one builds on another: a milestone's `depends_on` (earlier milestone ids) says what it waits on, and when it's left out it's inferred from its tasks' blockers in other milestones (none: it runs from the start). Each milestone has a goal, **pass criteria** (checkable statements) and **tasks**. A task has a stable id the agent picks (`auth-api`), a goal, context, acceptance criteria, an estimate, `touches` (the files it changes, so parallel tasks keep apart), **blockers** (tasks of the same or an earlier milestone whose code it builds on — never a later one, never a loop) and sub-tasks. A task is the agent's unless it's marked as yours (accounts, secrets, decisions).
- **Draft and approved.** A plan keeps a `draft` (the agent's and your working copy) and a `body` (what was approved). The draft lives with the plan in `~/.beluga/plans.json`, *never on the board*. **Approve** puts it there (`apply.ts`): new tasks are made with their sub-tasks and blockers wired up, changed ones rewritten (ticked criteria stay ticked), and tasks taken out are canceled. The milestone being worked on is Ready (status `todo`); later ones wait in the Backlog. Discarding a never-approved draft deletes the plan; the board never knew.
- **Changing an approved plan** makes a new draft: the page shows "Your agent proposes changes: 2 new · 1 changed · 1 taken out" with Apply / Discard. Your own edits apply at once (you're the approver). On **Autopilot**, the head agent's changes apply at once too.
- **Your planning style** (`~/.beluga/planning.md`, Plans › ⋯ › Planning Style…) is added to the agent's planning instructions every time.

### Planning with the agent

- **New Plan** (Plans, ⌘K): “Plan in {project}”, a big goal box that grows as you write (⌘↩ starts), and how it runs as three cards (names and sentences from `AUTONOMY_INFO`). Opened from a project it asks no project; `goal` prefills the box. It opens a conversation of its own in the project's main folder (the agent only reads there) and the plan's page. The agent reads the code and writes the plan with its tools (`beluga_plan`: `plan_get`, `plan_write`, `plan_update`); the graph fills in as it writes, and you talk it through in the conversation beside it. It also has the task tools, for a task that isn't part of the plan (the plan's own work stays in the plan until you approve it).
- **Plan with Tasks** in any conversation in a project (the composer's mode menu, or ⇧⇥: Act → Plan First → Plan with Tasks): that conversation becomes the plan's home. A strip above it shows the plan and its next step.
- A plan task can adopt a task already on the board (`issue: "BOB-12"`).
- **Staying one piece while it changes** (BLG-772). A plan keeps its own **decisions** (`decide`, `update_decision`, `remove_decision` ops, or `decisions` in `plan_write`): each has its text, `terms` (the words that mark text following it) and `retires` (old names). A new decision can `supersedes` an old one, which is kept, crossed out. Every `plan_write` and `plan_update` answers with warnings next to "Saved" (`coherence.ts`): near-identical task titles or goals, tasks in side-by-side milestones sharing `touches`, text naming ids that were just removed (and blockers dropped with them), empty milestones, and tasks still using a superseded decision's terms or a retired word. An id that's already in the plan is refused, never renamed. When the user changes direction, the planner is told to call `plan_get`, re-read the whole draft against the decisions and fix every task the change touches in that turn. The plan home's own board task (planning in a worktree that does a task) has its Goal and Decisions kept in step with the plan.
- **Verify, Then Approve** (`draft-review.ts`), only when you ask: Approve Plan's ▾ (on the plan's page and the strip above its conversation), ••• › Verify the Plan, or the phone's approve card. A separate agent reads the draft in a conversation of its own, folded into the plan, with only `plan_get` and `plan_review`. It looks for contradictions, duplicates, stale decisions and wrong order. If nothing needs fixing, the plan is approved (Verify the Plan alone just says so). If something does, the page lists it with **Fix**, which sends it to the plan's agent, and **Approve Anyway**. It never runs by itself: it takes a while, and the warnings already run on every change. While it works the page shows it moving (`verify-progress.ts`): how long it has been at it, its four checks (Contradictions, Duplicates, Stale decisions, Order) lighting up as its own lines name each one, its latest words, a soft sweep, and Watch It Work to open its conversation. The phone shows the same line and how many checks are done. The planner and the orchestrator of a running plan are both told to fit everything they add into the whole plan, re-reading it first.

### Running it (`pilot.ts`, `progress.ts`)

`planView` works out, from the plan, the board and what each worktree's agent is doing right now, every task's state (later · waiting · ready · agent working · needs you · in progress · in review · done), each milestone's (up next · in progress · agent is checking · ready to pass · check failed · passed) and **the one thing the plan waits for** (the page's main button). Every milestone whose dependencies have passed is open at once, each with its own check and pass; *Run at Once* counts milestones at work across the whole plan (each is one agent), and autonomy applies per milestone. The pilot acts on it a moment after anything changes:

| Autonomy | What happens |
|---|---|
| **Step by Step** (you start each task) | ready tasks line up with a Start button; nothing starts by itself. Start gives that one task to the milestone's agent (started for it the first time), which does only that and stops |
| **Check-ins** (`gated`, the default: runs, then waits for you at each milestone) | a milestone with work ready gets its agent by itself (up to *Run at Once*, 3 by default); each milestone waits for you to pass it |
| **Autopilot** (runs to the end, stops only if something fails) | milestone to milestone: a passing check moves on by itself; a failed one stops there, and the head agent adds fix tasks (applied at once) |

- **One agent per milestone** (BLG-7). A worktree per task spent most of each task finding its way around the code again, so an open milestone with work ready gets **one worktree and one agent** that does its tasks one after another, keeping its context. The pilot (`stepAgents`, `launch`) makes the worktree quietly from the plan's branch (or what its first ready task builds on), links every task of the milestone that's the agent's to it (`Board.linkWorktree(…, { shared })`; the first goes In Progress; the milestone's `runs[id].agent` records the worktree and the tasks handed to it), and sends one lean brief (`milestonePrompt`): the plan's goal, the milestone's goal and pass criteria, its tasks in the order they build on each other (`taskOrder`: blockers first, else the plan's order) each with its goal, context, files (`touches`) and checklist, what runs beside it, and how to go fast — read only what a task touches, no surveying the codebase, one task at a time: `task_update` In Progress, make it work, tick its criteria, typecheck and its own tests, **one commit per task**, `task_attach_proof`, a short handoff, `task_update` In Review, then the next without stopping; no pull requests. So the board still moves task by task, and the plan's view shows the next ones as *Next for this milestone's agent* (`TaskView.queued`). Each run in that worktree gets the milestone's note (`milestoneNote`, via `BoardWork.setRunBrief`) instead of one task's brief, and its task tools point at the task it's on. Its turn ending with tasks ready and none begun, it's sent on once (`milestoneNextPrompt`); stopping again with the same ones left, the plan says so and it's yours (open its chat, or Start one). A task of it that started and stopped is woken by the watchdog as before, once per worktree, and told to go on with the next. Tasks added later (a failed check's fix tasks) go to the same agent. Its worktree gone (archived), the next ready task gets a new one. Passing merges its one branch once and archives its one worktree. `workers: 'task'` (PlansWork/PlanPilot deps) keeps the older way, a worktree per task, described next.
- **Tasks for you** (assignee *me*) are never an agent's: the milestone's agent is told to skip them (what builds on one comes after you've done it), the plan's activity says “KEY waits for you”, and the pilot's `forYou` hook hears of each one once it's ready (`waitingOnYou`), for the plan's chat to ask you.
- **Starting** a task (a worktree per task, `workers: 'task'`) makes its worktree quietly (it doesn't take you there) with the agent on it. A task that builds on one still in review starts from that one's branch. One that builds on several starts from them combined: `beluga/<key>-base`, the first one's branch with the others merged in (`--no-ff`), made in a hidden worktree (`~/.beluga/workspaces/.bases/`, never listed) and removed once it's made. A branch already in another one, or already in main, isn't merged again. Meanwhile the task shows *Combining KLD-9 and KLD-27 …*. A conflict goes to the head agent, which may edit only that hidden worktree while the conflict is open. Once no markers are left, Beluga commits the merge, finishes combining and starts the task. If two fix-ups don't do it, the task waits for you and says where the conflict is. Beluga looks again every 30 seconds (or when you press Start), and the task starts once the conflict is fixed. A task already being worked on in a worktree is never started again (`BoardWork.start` refuses).
- **Finished** means In Review or Done. The task's agent is told to commit, rewrite the handoff and move its task to In Review when every acceptance criterion holds. A task can't go to In Review (by `task_update` or its pull request opening) while a criterion is neither ticked nor explained: its agent is told which, and the board shows **Needs its checks** until they are (then an open pull request moves it by itself). On Autopilot, a task whose agent stopped without finishing is nudged once.
- **The plan's branch.** Approving a plan makes `plan/<slug>` from main (its title up to a colon; a `plan/<name>` its text names, or one that already exists, is adopted, never made twice), stored on the plan. Every task starts from it as it is right then, so a later milestone sees the earlier ones' work. Passing a milestone (you, or the agent on Autopilot) merges each of its task branches `--no-ff` into it, in a hidden worktree (or where the branch is already checked out, if that checkout is clean). Branches already in it are skipped. The milestone counts as passed only once the merge is done. Then its tasks go **Merged into Plan** (status `in_plan`), a board column between In Review and Done, and their worktrees are archived (the conversations are kept) and their branches deleted. No PR is opened per task or per milestone. A conflict goes to the head agent as a fix-up in that worktree; meanwhile the plan says *Fixing a merge conflict in KEY* and the milestone stays open. When the last milestone passes, the plan offers **Open PR** (`plan/<slug>` → main, then Merge on GitHub) or **Merge into Main Locally**. When that PR merges, every Merged into Plan task goes to Done with *merged into main via #N*. A PR closed without merging leaves them Merged into Plan and says so on the plan. The pilot looks at the PR every 2 minutes (`PlanGit`, `plan-git.ts`). Merging it works as a worktree's does: GitHub is asked first (a PR merged or closed meanwhile says so), the branch is pushed, and GitHub's no comes back in plain words; with checks or a review pending the button is **Merge When Checks Pass** (`--auto`). A PR that conflicts with main offers **Resolve Conflicts**: main is merged into the plan's branch in the same hidden worktree, a conflict goes to the head agent like a milestone's, and once it's in the branch is pushed. A conflict the agent couldn't fix waits for you with **Ask Claude Again** and **Show Conflict in Finder** (also a Needs You card on the phone). A milestone whose merge fails for another reason (a dirty checkout) keeps why on it (`mergeFailed`) until it's passed again. The page's big steps say what's under way on their button, and a step that fails stays on the page with **Try Again**. **Where the work goes** (the branch button over the canvas) lists main, the PR, the plan's branch and each milestone with where it stands. Plans that ran before this catch up once: each passed milestone whose tasks are still In Review is merged into the branch, and tasks already in main go to Done.
- **Pass Anyway is instant** (BLG-16). Passing is said at once (the page shows it merging) and nothing slow sits on the request: the merge into the plan's branch starts right away in the background, and archiving the merged worktrees runs after it, so another milestone's merge never waits for it. A check the head agent still runs when you pass is stopped (`AgentHost.cancelRun`; or taken out of the queue), so what the plan asks next (a fix-up, the next check, the recap) doesn't wait behind a test run nobody needs, and a verdict that comes late is ignored.
- **A checker per milestone.** A milestone's check isn't the head agent's: it gets a **checker of its own**, a fresh agent in a conversation made for it in the project (`PilotDeps.checkerChat`, recorded as `runs[id].checker`, folded into the plan like its home and worktrees). It didn't write the code nor plan it, and it has only `plan_get` and `plan_gate` (for its own milestone). So the plan's conversation stays free for you while it checks, and milestones that finish together are checked side by side. Its verdict reaches the head conversation as one line; a failed one also goes to the head agent with the notes, to add the fix tasks (applied at once on Autopilot). A later round goes to the same checker, which remembers what failed. Passing archives it (what it said is kept). With no conversation to make, the head agent checks as before.
- **A plan never stalls quietly** (BLG-473, `rescue` in `pilot.ts`). One rule, milestone by milestone: an open milestone with the agent's work left (ready or stopped tasks, a check, a merge, fix tasks on Autopilot) where nothing of it runs and nothing of it waits on you is stalled. After 3 quiet minutes Beluga moves it along, a step further each time it stays stuck: send its agent on (or wake the stopped task, or ask for the check again), then a fresh agent (what was left of the turn stopped and started over, or a fresh checker), then the head agent decides with its tools. Only then is it yours: the plan says what it's stuck on and what was tried. A new kind of stall starts its ladder over, with at most 6 steps per milestone in all. Each milestone has its own ladder, so one stuck behind another's check is still seen. The ladder is kept on the plan (`plan.rescue`), so a restart goes on from there, and it starts over as soon as that milestone moves (a task finished, a verdict, a merge, a pass). Things that are yours stop it: a pass on Check-ins, a task for you, a question or an approval, a step-by-step start. `tests/plans.test.ts` › soak runs a five-milestone plan on Autopilot with agents that stop early or never answer, checkers that never record a verdict, and a restart, and it reaches the end by itself.
- **Everything an agent starts ends with its turn.** Nothing wakes a run whose turn ended, and what it started is stopped, so checks and the head agent are told to run each command to the end inside their turn (`WAIT_IN_TURN`). A check that ran the e2e in the background and waited to be woken is what stalled plans before.
- **A check never ends silently.** Every check must end with `plan_gate`, never by asking how to go on. A check whose turn ends without a verdict is asked once more (`watchCheck`); ending without one again, the plan says so and it's yours (open its conversation, or Check Again). On Autopilot the head agent is told never to end a turn waiting for you, except for a task assigned to you, a secret or an account.
- **Gates:** when a milestone's tasks are finished, its checker checks its pass criteria for real (briefs, handoffs, proof, diffs) and records `plan_gate` pass or fail with notes per criterion. The check lists each task's acceptance criteria with ticks and reasons: an unexplained one fails the milestone, a deferred one waits for the last milestone's check, which must settle every deferred item against the full suite run (tick it, or fail with a fix task). A milestone with no pass criteria of its own is still checked when one of its tasks has an open criterion. While it checks, on every mode, the plan waits on the agent (`checking`), never on you; it's yours to pass only once the check is back (or there's nothing to check). Pass Milestone / Not Yet… are yours (Not Yet sends what's missing to the head agent, which adds the tasks). When the last milestone passes, the head agent writes a recap.
- **Parallel agents know about each other.** Every run doing a task gets what else in the project is being worked on right now (which task, which worktree, whether its agent is working); `task_get` says where a task is being worked on. A plan task's worktree also gets its plan, milestone, pass criteria and the tasks running beside it (with their `touches`). The head agent is warned when tasks running side by side touch the same files, and can message a task's agent (`plan_message_task`).
- Pause stops starts; the scheduler, not the agent, enforces limits, blockers and gates.
- **Tests, sized to the task.** A task writes the tests it needs and runs only typecheck and the test files it touched. The e2e and full suites run once per milestone, at its check, on the milestone's combined work. With *When to Run Tests ▸ Only at the End* (⋯, or the New Plan sheet), milestone checks skip the suites and the final step runs everything. A failure that looks like load counts only if it fails again when re-run once, alone.
- **One Mac e2e at a time.** `npm run e2e` (packages/mac) runs through `scripts/e2e-lock.mjs`: a machine-wide lock (`~/.beluga/e2e/lock.json`), so a second run from any worktree waits ("waiting for KLD-12's e2e"). Each worktree gets its own port and demo home. Every process the run starts is stopped however it ends, and a run that failed while the Mac was overloaded re-runs its failed tests once, alone. When a worktree's agent stops, Beluga stops the test runs it left (its runs carry `BELUGA_WORKTREE`). Archiving or deleting a worktree stops every test runner in it (`src/workspaces/test-procs.ts`).
- **What happened:** the pilot writes what it did to the plan's activity: tasks `started` and `finished` (coming back for review), the agent `checked` a milestone (or it `failed`), milestones `merged` and `passed`, the mode changed (`autonomy`).

### In the window (`packages/mac/src/plans/`)

- **Plans** in the sidebar (under Tasks): one project's plans with a milestone progress bar, their status and what they wait for.
- **A plan is one row under its project** (`layout/plan-row.tsx`): a flag, its name, a small ring of how far it got (breathing while its tasks run), a dot when it waits for you, and a count of what's new in its conversation and its tasks. Its conversation and its task worktrees (`core/plans/owner.ts`: any worktree of a task of a running plan, adopted tasks included) stay off the tree; the row opens the plan with its conversation, and stays marked while you're in one of its tasks. Project Home lists plans the same way and leaves their worktrees out; the Worktrees page still lists them, labelled with their plan.
- **A running plan is a black box at the top level.** One rule (`planOf` / `isPlanOwned` in `core/plans/owner.ts`) says which conversations fold into a plan, and every top-level place follows it: Unread shows the plan once ("Card checkout for launch · 3 updates") and only while something in it is new; a task's question or approval makes that row need you, saying which ("KLD-12 asks a question"), and opens the plan at that task, where Answer is one click. The bell folds a plan's quiet task news under one entry (milestones stand alone), and Overview and project tallies count the plan as one item. Inside the plan each task's card and row keep their own unread mark. For the detail, the plan's ⋯ › Show Task Chats in the Sidebar lists them under its row (per plan, off by default).
- **A plan task's worktree has no local Merge**: its next step is **Open Plan** (and **Open Task** under ⋯); **Merge Anyway…** (and ⇧⌘M) first says Beluga merges it into the plan itself. No PR of its own either: the plan opens one at the end.
- **A plan's page:** the name (renamed in place), one progress bar (milestones that run side by side share a column, as stacked tracks), and one sentence with whose turn it is (`headline`: “You: pass “API” — the agent checked all 4 criteria”, “The agent is checking “API””, “3 tasks running in 2 milestones”, “Fixing a merge conflict in KLD-9”); clicking it opens **What Happened**, the plan's feed (newest first, repeats folded: “Beluga started 3 tasks: …”). Beside it: **Runs on Check-ins**, a button that opens the three mode cards; picking another says in plain words what changes from now on (and what happens at once) before you switch. Then ⋯ (Pause, Run at Once ▸, When to Run Tests ▸, Copy as Markdown, Planning Style…, Discard, Delete), and one main button for what it waits for (Approve Plan, Apply Changes, Start, Pass Milestone, Not Yet…). A task's worktree shows the same sentence from the task's side (“Done. The agent is checking “API”; Beluga merges this into the plan”).
  - **Graph:** milestones that run side by side sit side by side in a row; a row waits on the rows above, and a line runs from each milestone down to those that wait on it. Tasks inside left to right by what waits on what (what can start at once lines up on the left); a gate at the end of each lane that opens the next. Tasks the agent is working on have a copper light going round them and say what the agent is doing; finished ones tick; a gate waiting for you is the one thing in the accent. The layout depends only on the plan's shape, so work moving on never moves anything; a re-cut plan glides to its new shape. Blockers from an earlier milestone show for the task you pick.
  - **Outline:** the same, milestone by milestone, with names changed in place and a task's ⋯ (Start, Move to ▸, I'll Do It Myself, Take Out of the Plan).
  - Picking a task or gate opens its details (goal, done when, waits on, the files it changes, the agent's check).
  - **The conversation** with the plan's agent docks on the right.

### Kanban drag

The board's cards are picked up with the pointer (`TaskBoard.tsx`, pure parts in `board-drag.ts`): the card lifts and leans with the way you move it, the cards where it would land slide apart (motion layout springs), and it settles into place on release. Esc puts it back; the board scrolls near its edges; ⌥←/→ and ⌥↑/↓ move a focused card. A card dropped there rests a moment, then folds away with its column.
